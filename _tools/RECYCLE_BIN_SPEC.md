## 2. 两类作品，两套机制（重要）

本站作品有**两个完全不同的来源**，删除方式因此不同：

### A. 投稿作品（数据库 `photos` 表）

状态机在 v2.6.0 扩展为：

```
pending（待审核）
   ├─ 通过 → approved（已发布，官网可见）
   ├─ 拒绝 → offline（已下架）
   └─ 移入回收站 → trash ─┬─ 恢复到已下架 → offline
                          └─ 永久删除 → 删数据库行 + COS 公开图 + _original/ 私有原图
approved / offline 也都可以直接移入 trash
```

- `status` 列是纯 `text`、无 check 约束，**新增 `trash` 取值不需要跑任何 SQL**。
- 官网 `/api/photos` 只返回 `approved`，`trash` 天然不可见。
- 恢复只到 `offline`，**不会直接发布**——避免手滑把不该发的图推上官网。
- 投稿人自查（`photo-status`）看到 `trash` 会显示「未通过」，且按既有安全规则不返回图片地址。

### B. 静态老作品（`assets/data/works.js`，78 张）

`works.js` 和 `assets/img/works/*.webp` 是**仓库静态文件**，Vercel 运行时只读，
后台接口无法物理删除，改了也会被下一次部署覆盖。因此采用**逻辑删除**：

```
后台写入 COS 私有语义对象  _config/hidden-works.json
   { "hidden": ["hanlou-01"], "purged": ["sports-01"] }
        ↓
公开只读接口 GET /api/static-works
        ↓
site.js 的 visibleWorks() 过滤 → 首页精选区 + 作品集都不再渲染这些 id
```

- 清单里只有作品 id（与公开的 `works.js` 一致），**不含隐私**。
- `hidden` = 回收站，可撤销；`purged` = 永久移除，后台仍保留「撤销」入口
  （因为图片文件删不掉，留一个后悔药比假装不可逆更诚实）。
- 桶是「公有读私有写」：写必须签名，服务端自访不受匿名策略影响。若希望
  连清单也完全禁止匿名读，可在 COS 控制台按 `_backup/*` 同款加一条 Deny
  匿名 GetObject 的 `_config/*` 策略——**可选，不影响功能**。
- 降级原则：清单读失败时公开接口返回空清单（宁可多显示，也不能因配置抖动
  让整站作品消失）；后台写操作则显式报错，避免「读失败 → 当空 → 覆盖」抹掉已有清单。

## 3. 接口契约

### `GET /api/static-works`（公开，无需密码）

```json
{ "ok": true, "hidden": ["hanlou-01"], "purged": [], "excluded": ["hanlou-01"] }
```

失败降级：`{ "ok": false, "hidden": [], "purged": [], "excluded": [], "error": "…" }`。

### `POST /api/admin`（沿用单密码）

| action | 参数 | 行为 |
| --- | --- | --- |
| `trash` | `id` | 任一状态 → `trash`，**不删任何文件** |
| `restore_trash` | `id` | `trash` → `offline` |
| `static_set` | `id`, `state` | `hidden` / `purged` / `visible` |
| `delete` | `id` | 永久删除（回收站内使用），删行 + COS 文件 |
| `batch` | `ids`, `op` | `op: "trash"` 批量软删；`op: "delete"` 批量永久删；`op: "approve"` 不变 |
| `list` | — | 响应新增 `trash: []` 段 |

`static_set` 的 `state` 非法或缺少 `id` 返回 400；未带正确密码返回 401。

## 4. 备份与恢复

- 月度备份（`api/_lib/backup.js`）除两张 CSV 外，新增
  `_backup/<YYYY-MM>/static-works-<YYYY-MM>.json`，内容含 `stamp / ok / hidden / purged`。
- **为什么必须备份它**：清单丢了，被删除的老作品会重新出现在官网。
- 清单读取或写入备份失败不会阻塞两张主表 CSV（响应里 `staticOk: false` 会标出来）。
- 恢复：下载对应月份 JSON，把 `hidden` / `purged` 写回
  `_config/hidden-works.json`（COS 控制台上传，或在后台对每张重新操作）。
  桶已开启版本控制，误覆盖可按版本 ID 回滚。

## 6. 已知边界与风险

1. **静态老作品无法物理删文件**：「永久移除」只是从展示清单剔除，
   `assets/img/works/*.webp` 仍在仓库里占空间。要彻底清理需改 `works.js`
   并随某次发版删除文件（非后台能力，也不会自动发生）。
2. **首页/作品集是异步过滤**：清单通过 `fetch` 加载，极慢网络下被删的老图
   可能短暂闪现一帧后消失。清单为空时零开销、零闪烁。
3. **`_config/*` 默认匿名可读**：内容仅 id，无隐私；介意的话按第 2 节加策略。
4. **回收站不是无限仓库**：软删保留 COS 图片会持续占存储（量很小），
   定期在回收站做一次永久删除即可。COS 版本控制已开启，删除也留历史版本。
5. **并发写清单无锁**：后台是单密码单干部操作场景，两人同时改不同老作品
   理论上可能后写覆盖先写。规模不构成问题，若将来多管理员需给清单加版本校验。
